# Battlefield 2 gameplay data survey (for a Rust/Bevy reimplementation)

Install surveyed: a retail install (1.5 + Special Forces + Booster packs). All archives were read in place with Python `zipfile`; nothing was extracted. Numbers below are taken from the actual files unless marked:

- **[verified]**: read directly from the data.
- **[inferred]**: my interpretation of the data's structure (strong evidence, no confirming document).
- **[community]**: semantics from modding sources (listed at the end).
- **[unknown]**: not recoverable from data. Needs measurement or binary RE (§11).

The tables were generated by throwaway scripts during research; the tested parsers are in `tools/reference/`.

---

## 0. TL;DR: the most important findings

1. **The data tells you *what*, the engine keeps *how*.** Every number a designer tuned is in `.con`/`.tweak`/`.ai`/`.py`: masses, torques, gear ratios, wing lift coefficients, spring strengths, rates of fire, deviation parameters, damage, material matrix, ticket rates, bot weights. The formulas that consume them are in `BF2.exe` / `bf2_w32ded.exe` (physics, deviation, damage falloff, netcode) and `AIDLL.dll` (bots). Examples: how `setWingLift 2.5` becomes newtons, and what `grip 8` means.
2. **One uniform object model.** Everything is an `ObjectTemplate.create <Type> <name>` node: a typed property bag plus a child list (`addTemplate` + `setPosition`/`setRotation`). There are 64 template types (census in §2). A vehicle is a `PlayerControlObject` root with a tree of `RotationalBundle` joints driven by input axes, plus force generators (`Engine`, `Wing`, `Spring`, `ForceObject`, `FloatingBundle`), `GenericFireArm` weapons, `Camera`s, `EntryPoint`s and nested `PlayerControlObject` seats. A Rust ECS maps onto this cleanly.
3. **Damage is `projectile.damage × damageMod[projectileMaterial][hitMaterial]`.** The matrix (`Common_server.zip:Material/materialManagerSettings.con`) has 5,054 cells over 143 materials. Soldiers use per-bone capsule materials (head ×3, limbs ×0.7, body-armour ×0.66). Vehicles use per-collision-part materials for direct hits and `armor.defaultMaterial` for splash. **Healing, repairing and resupply go through the same matrix** (materials 73/84/91), so one system covers all of it.
4. **All game-mode rules live in about 2.5k lines of Python 2.3.4**, calling a small `host.*` C API (≈45 functions, 37 events; full list in §9). Conquest (`gpm_cq.py`) is 621 lines: flag capture, ticket bleed and scoring. It is cheap to port to Rust verbatim. A compatibility layer for the original Python is possible but low value (Python 2 syntax, engine-object semantics).
5. **Bots are data-configured.** Per-object `aiTemplate` plugins cover sensing, mobility, a PD-controller input mapping and armament. `weaponTemplate`/`kitTemplate` hold range and strength-versus-target-class tables. `AIBehaviours.ai` holds utility-style behaviour selection (13 behaviours × 15 "vehicle" classes, urgency curves, weight sets and a plan-step interpreter). A simple strategic commander (`aiStrategy`, per-layer `StrategicAreas.ai`) sits on top. The behaviour code itself is in `AIDLL.dll`.
6. **The navmesh intermediate format is now decodable.** `GTSData/Output/*.qti` is an SoA triangle mesh (vertices as f64 triples, triangles, a per-face vector, a per-face material byte, neighbours). `*.cls` holds the triangle clusters. I verified both byte-for-byte against the text twins (`*.qti.txt`, `*.cls.txt`, `*.obj`) that ship in 13 levels. The runtime files (`AIPathFinding/*.qtr`, `*.clb`) are raw MSVC struct dumps with `0xCD` padding and are not worth reversing. `AerialHeighMap.ahm` is trivial. Recommendation: **generate our own navmesh with Recast from our collision data.** Keep `StrategicAreas.ai` as-is, and optionally use `.qti` as a reference or fallback.
7. **Recommended RE scope:** decompile a few specific functions (wing lift, engine/gearbox/`newCar2` tyre model, helicopter engine, deviation accumulation, damage falloff and defaults) in `bf2_w32ded.exe`. In parallel, **measure the running original game with its own Python API**: a 30 Hz timer logging `getPosition`/`getRotation` of vehicles gives trajectories to fit against. Netcode RE is not worth it: we will not interoperate, so design our own.

### 1.2 Script syntax (census across every `.con`/`.tweak`/`.inc`, levels included) [verified]

- Line-oriented `Namespace.command arg arg …`, **case-insensitive** (both `ObjectTemplate.activeSafe` and `Objecttemplate.addTemplate` appear). Comments: `rem`, and `beginrem`/`endrem` blocks.
- Control flow: `run file [args]` (7,984×), `include file` (2,832×), `if v_arg1 == host` / `else` / `endIf` (704×), `var v_x = …` (9×). Arguments `v_arg1…v_argN` are passed by `run`. Example: level `Init.con` runs different branches for `BF2Editor` and for the game.
- Vectors are `x/y/z` with no spaces. Random distributions look like `CRD_NONE/6/0/0` (constant 6) or `CRD_UNIFORM/0.1/0.6/0` (uniform 0.1..0.6). `CRD_NORMAL/1/1/0` also appears.
- Top namespaces by line count: `ObjectTemplate` 396k, `Object` 258k (instances in levels), `MaterialManager` 12.8k, `CombatArea` 12.4k, `AnimationSystem`/`AnimationBundle`/`AnimationTrigger` ~33k, `GeometryTemplate` 11.4k, `gameLogic` 2.0k, `CollisionManager` 1.7k.
- **Template authoring pattern:** the `.con` file declares the hierarchy (`ObjectTemplate.create …`, `addTemplate`, `setPosition`, `geometryPart`/`collisionPart` indices into the mesh). It then `include`s a `.tweak` that re-opens each template with `ObjectTemplate.activeSafe <Type> <name>` and sets the gameplay properties. `ObjectTemplate.active <name>` also re-opens a template.
- **Child binding:** `ObjectTemplate.addTemplate X` appends a child. The next `setPosition` and `setRotation` apply to *that child's placement* (yaw/pitch/roll in degrees). The same child template can be added several times (6 flare barrels, 6 Hydra barrels, 2 antennas).
- **Components:** `ObjectTemplate.createComponent <CompType>` followed by dotted properties, e.g. `ObjectTemplate.fire.roundsPerMinute`, `ObjectTemplate.ammo.magSize`, `ObjectTemplate.armor.maxHitPoints`. The prefix is the component *slot* (`fire`, `ammo`, `recoil`, `deviation`, `zoom`, `armor`, `target`, `seek`, `follow`, `detonation`, `collision`, `penetrate`, `ik`, `radio`, `ability`, …).
- **Repeated properties are lists, not overrides:** `fire.addFireRate` (fire-mode list), `mapMaterial i name id`, `armor.addArmorEffect`, `setObjectTemplate team tmpl`, `addTemplate`, `seatInformation`. Everything else is last-write-wins. Some duplicates exist (the M1A2 sets `worldFOV` twice), so a loader must tolerate them.
- **Instances:** levels create instances with `Object.create <template>`, `Object.absolutePosition x/y/z`, `Object.rotation`, `Object.layer <n>` and `Object.setControlPointId <id>`. Layers correspond to the 16/32/64 player sizes (`GamePlayObjects.con` exists per mode and size).

**Loader recommendation:** parse into a generic `TemplateStore { name → Template { ty, props: Vec<(key, args)>, children: Vec<ChildRef{name, pos, rot}> } }` with case-folded keys. Then build typed views (`VehicleDef`, `EngineDef`, `FireArmDef`, …) with explicit defaults. Keep raw props for debugging and for unmodelled keys. My Python parser (`parse.py`) does exactly this in about 50 lines and parses 11,771 unique templates.

## 3. Physics primitives: semantics and what is unknown

### 3.1 General rigid body [inferred + unknown]

- One rigid body per root PCO, with `hasMobilePhysics 1` and `physicsType Mesh` (collision mesh with numbered parts that children reference via `collisionPart`). Children with `hasMobilePhysics 1` move kinematically relative to their parent: turret rotation changes the collision shape but not the body.
- `mass`: engine units, not real kilograms (M1A2 6,000 vs 62 t in reality; F-18 5,000; soldier 100). `inertiaModifier` scales the auto-computed inertia tensor (all jets use `0.4/0.4/0.4`, the parachute `3/3/3`). The inertia tensor itself comes from the collision mesh [unknown formula].
- `drag` is a scalar coefficient (jets 0.05, tanks 2, helicopters 1–2). `dragModifier x/y/z` is a per-local-axis multiplier (helicopters `1/1/0.75`: less drag forward). Drag law (linear or quadratic in v) [unknown].
- `gravityModifier` multiplies world gravity: ground vehicles 1.5–2.0, bullets absent (1.0?), tank shells 0.4, rockets 0.05–0.1, Sidewinder −2 (climbs). The world gravity constant is not in the data [unknown; likely 9.81].
- `floaterMod` controls buoyancy (0 = sinks; boats and amphibious APCs 0.5–0.9).
- `centerOfCollisionOffset 0/0.4/0` shifts the centre of mass.

### 3.2 Engines

Engine output is the engine joint's "rotation" state: the value that `setMin/MaxRotation` limits and that input ramps at `setAcceleration` up to `setMaxSpeed`. It acts as throttle/RPM.

- **Tank (`c_ETTank`)** [verified values]: M1A2 has `setTorque 10`, `setDifferential 12`, `setGearUp 0.95`/`setGearDown 0.45`/`setGearChangeTime 0.1` (no ratio list), throttle mapped to roll with range ±1, yaw input ±1 for skid steering with `trackTurnAcceleration 30` and `trackTurnSpeed 0.85`. Road wheels are `Spring`s: the end wheels have `setStrength 14`, `setDamping 3`, `grip 8`. The middle wheels have strength 0 and `grip 128`. Drive sprockets are `RotationalBundle`s with `grip 128` and `rotateAsAnimatedUV` (visual). **So tanks ride on only a few "real" contact springs**, and the rest is cosmetic.
- **Wheeled (`c_ETNewCar2`)**: a full drivetrain and tyre model. LAV-25: `setTorque 225`, `setDifferential 5.5`, `setNumberOfGears 4`, `setGearRatios 2.45 1.35 1 0.6 0.6`, `setGearUp 0.85`, `setGearDown 0.4`, `setGearChangeTime 0.7`, `newCar2.minRpm 1000`, `maxRpm 4000`, `wheelInertia 200`, `engineFeedbackMod 0.6`, `brakeTorque 5000`, `engineBrakeTorque 2500`, `frictionTorque 100`, `frictionMod 1.5`, `slopeTorqueMod 1`, and Pacejka-like slip curves per axis: `wheelLongFrictionMod 1`, `wheelLongDriveFrictionMod 1.4`, `wheelLongPeakAt 0.1`, `wheelLongMinDynamicFriction 0.7`, `wheelLongScale 0.1`, `wheelLatFrictionMod 3`, `wheelLatDriveFrictionMod 0.3`, `wheelLatPeakAt 0.2`, `wheelLatMinDynamicFriction 0.7`, `wheelLatScale 0.1`. Steering uses `RotationalBundle`s with `setInputToYaw PIYaw`, ±30°. The data strongly suggests a slip-ratio curve that peaks at `…PeakAt` and decays to `…MinDynamicFriction`, but the exact curve is [unknown]. It is a good candidate for fitting by measurement.
- **Plane (`c_ETPlane`)**: F-18 uses two engines, each `setTorque 100`, `setDifferential 10`, `setMaxRotation 0/0/5000`, `setMaxSpeed 0/0/150`, `noPropellerEffectAtSpeed 125` (thrust fades towards zero at ~125 m/s, which effectively sets top speed). Afterburner comes from the PCO `sprintFactor 1.6` with `sprintDissipationTime 10` and `sprintRecoverTime 30` (s).
- **Helicopter (`c_ETHelicopter`)**: the main rotor Engine hangs under the rotor-head joints and inherits their tilt. The thrust direction therefore follows cyclic input (details in §5.3). The tail rotor is a second Helicopter engine with `pureRotational 1` (yaw torque only). Several "arcade assists" are explicit parameters (`horizontalSpeedMagnifier`, `dampHorizontalVel(Factor)`, `decreaseAngleToZero*`).
- **Ship (`c_ETShip`)**: jetski `setTorque 120`, `setDifferential 3.2`; amphibious APCs have a second `Ship 15/40` engine for water propulsion.

**Unknown:** how torque × differential × gear ratio × RPM becomes wheel torque or thrust force; the gearbox automation; the RPM model; heli collective behaviour. All need RE or fitting.

### 3.4 Wings [verified values; formula unknown]

Lift appears to be ∝ ρ·v²·(`wingLift` + `flapLift`·deflection) along the wing normal at the wing position, with the deflection in [−1, 1] from the input. The fact that jets are flyable with `drag 0.05` and `inertiaModifier 0.4` suggests heavily game-tuned lift. `setPitchOffset` offsets the application point or angle. Treat everything here as [unknown] until fitted.

**The rotor-head trick [verified, inferred purpose]:** `Rotorhead` is placed 20 m *below* the hull origin and `Rotorhead2` 20 m back up. Cyclic tilt of the outer joint therefore swings the whole engine assembly around a pivot 20 m below. The inner joint counter-rotates (opposite acceleration sign), so the engine keeps an almost-level orientation but is *translated* sideways and forwards. The net effect is a thrust point offset that creates the pitching and rolling moment, while a thrust vector tilted by the resulting small angle drives translation. Reproduce this by modelling the rotor as a force at a point that is offset proportionally to cyclic input and tilted by a small angle. Do not copy the 20 m geometry literally.

### 6.4 Deviation (spread) model

Semantics [community, Project Reality forum; consistent with the data]:

- `deviation.minDev d`: base cone in degrees, multiplied by `devModStand` / `devModCrouch` / `devModLie` for stance and by `devModZoom` when zoomed. Best possible spread = `minDev × devModLie × devModZoom`.
- `setFireDev max add decay`: each shot after the first adds `add`, capped at `max`; the value decays by `decay` **per server frame (30 Hz)**.
- `setTurnDev max perYawDeg perPitchDeg decay`: added per degree of mouse turn. All vanilla rifles use `0 0 0 0` (off).
- `setSpeedDev max perForward perStrafe decay`: added from movement.
- `setMiscDev max perJump decay`: added by jumping or landing.

Reconstructed algorithm (the exact combination is [unknown]: additive vs max, whether stance and zoom scale the accumulators, and the cone sampling distribution):

```
fireAcc  = min(fireAcc  + add_fire,                        max_fire);  fireAcc  -= decay_fire  per 1/30 s
speedAcc = min(speedAcc + vFwd*k_fwd + vStrafe*k_strafe,   max_speed); speedAcc -= decay_speed per 1/30 s
miscAcc  = min(miscAcc  + (jumped ? add_jump : 0),         max_misc);  miscAcc  -= decay_misc  per 1/30 s
cone_deg = minDev*stanceMod*(zoomed ? devModZoom : 1) + fireAcc + speedAcc + miscAcc (+ turnAcc)
dir      = aim rotated by a random offset inside cone_deg     (uniform vs gaussian: unknown)
```

Vehicle guns use `SimpleDeviationComp` with only `minDev` (M2HB 0.1, coax 0.25, F-18 cannon 0.025, smoke/flares 5–6). The HUD crosshair spread is driven by `weaponHud.deviationFactor 5`, `minVisualDeviation 2` and `maxVisualDeviation 20`.

| M16A2 | 0.3 | `2 0.2 0.05` | `1 0.2 0.2 0.1` | `3 1.5 0.05` | 1.5 / 1.3 / – / 0.8 |

### 6.7 Projectiles, explosions and the damage formula

- Direct hit [inferred, community-consistent]: `damage_applied = projectile.damage × damageMod[projectile.material][hitMaterial] (× falloff)`. `hitMaterial` is the soldier bone capsule material or the vehicle collision-part `mapMaterial` id.
- **Falloff:** only 14 projectiles set `distToStartLoseDamage`/`distToMinDamage`. Pistols use 100 → 200 m with `minDamage 8` (of 20). Shotguns use 30–40 → 100 m with `minDamage 8`. The M82A1 uses 300 → 600. This suggests a linear interpolation from `damage` to `minDamage` (absolute) between the two distances [inferred]. Behaviour when the distances are unset (all assault rifles, which also set `minDamage 0.2` or `1`) is [unknown]. It is either no falloff or engine-default distances.
- Explosions: `detonation.explosionDamage` at the centre, falling off over `explosionRadius` (curve [unknown]; linear is the common assumption). The matrix row is `explosionMaterial` and the column is the victim's **`armor.defaultMaterial`**. Vehicles set their defaultMaterial to the "Blast_sensitivity" materials 71/72/110, whose rows tune splash per vehicle class: blastwave 70 → hard object 72 = 0.05, grenade 69 → 72 = 0.4, C4 80 → 72 = 0.7, vehicle explosion 99 → 72 = 2.5. `explosionForce` is an impulse, scaled on the victim by `armor.explosionForceMod` and capped by `explosionForceMax`.
- Penetration: materials carry `damageLoss`/`minDamageLoss`/`maxDamageLoss`, `penetrationDeviation`, `projectileCollisionHardness` (ricochet), `isOneSided`, `overrideNeverPenetrate` and `isSeeThrough`. Projectiles opt in with `penetrate.allowSolidPenetration 1` (17 projectiles). `DefaultRicochetComp` uses `projectileCollisionHardness`.
- Soldier death flow: HP ≤ 0 puts the soldier in the "man down" state (the Python event `PlayerKilled` fires). The soldier is revivable during `sv.manDownTime 15`. `PlayerDeath` fires on actual death, which costs a ticket. Defibrillator projectile: `ResurrectCollisionComp` with `collision.resurrectDamage 20000`, `collision.restoreHP 120` (units [unknown]), `damage 1000`, `damageMandownSoldiers 1`, material 89 (Soldier_resurrection).

### 6.8 Medic, engineer and support actions [verified]

- Heal, repair and rearm are "negative damage" delivered through the material matrix. Row 73 (Soldier_healing) = 1 against human materials and 0 against armour. Row 84 (Engineer_repair) = 1 against armour, 10 against Destroyable_obj_small and 0 against humans. Row 91 (Ammo_replenish) = 1 against both. Using the same pipeline for damage and all three support actions is elegant: one system covers everything.
- `medikit`: `ThrownFireComp` + `ReplenishingAmmoComp`. Held: `abilityRadius 4`, `abilityStrength 5.3` (HP/s [inferred]), `abilityDrain 0.05`. Thrown bag: `abilityCost 0.33`, projectile `medikit_Projectile` with `ReplenishDetonationComp` (`triggerRadius 1`, `triggerType MTYPco`, `replenishingType RTHeal`, `replenishingStrength 100`), `armingDelay 2`, lifetime 9,999 s, up to 5 in the world.
- `ammokit`: the same with `RTAmmo` and material 91. `wrench`: SingleFire 60 rpm with `abilityStrength 3`, `abilityDrain 0.06`, `onlyActiveWhileFiring 1`, material 84, firing a `BlankProjectile`. `defibrillator`: `abilityCost 0.3` per shock.
- The kit's ability "energy" regenerates at `abilityRestoreRate` (0.04–0.05 per second). In vehicles, the medic, engineer and support kits heal, repair or rearm occupants within a 7 m radius at `abilityInVehicleStrength`.
- Score callbacks: `PlayerHealPoint`, `PlayerRepairPoint` and `PlayerGiveAmmoPoint` fire each time the accumulated amount crosses the limit set in Python (`setHealPointLimit(100)` etc.).
- Static supply: `SupplyObject` (`healSpeed`, `refillAmmoSpeed`, `damageSpeed` = repair speed, `radius`, `workOnSoldiers`/`workOnVehicles`, `teamFromClosestCP`). Commander supply crates are dropped from `gameLogic.supplyDropHeight 50` and live for `supplyDropNumSecsToLive 300`.

### 8.2 Conquest logic (`gpm_cq.py`) [verified]

**Setup (on GameStatus Playing):**

- For every `ControlPoint`, create a radius trigger (hemispherical if `isHemisphere`) with the template `radius` over `<<PCO>>` objects.
- Starting tickets = `startTickets × sv.ticketRatio/100`.
- Ticket limits: id 1 = 0 (game over), 2 = 10, 3 = 10%, 4 = 20% (warning state).
- Register the handlers: `PlayerDeath`, `PlayerKilled`, `PlayerRevived`, `PlayerSpawn`, `EnterVehicle`, `ExitVehicle`, `ControlPointChangedOwner`, `TicketLimitReached`, `TimeLimitReached`.

**Capture (`onCPTrigger`, called on any enter/exit/kill/revive/vehicle change near a CP):**

1. Skip if `unableToChangeTeam`.
2. Count occupants per team. Only alive, not man-down, not-killed players count, and **only the first occupant of each vehicle** (everyone else is told "exit to capture", HUD event 66/49).
3. `overweight = team1 − team2`; the attacking team is the side with the majority.
4. If nobody is present, the flag drifts back towards the owner: `attackOverWeight = ±0.5` using `timeToLoseControl`.
5. If the flag already shows the attacking team (or it is neutral at the bottom), raise it at `|overweight| / timeToGetControl` per second. Otherwise lower it at `|overweight| / timeToLoseControl`.
6. The flag colour can change only when the flag is at the bottom.
7. The script writes `takeOverChangePerSecond` into the CP. **The engine integrates flag height** and calls `ControlPointChangedOwner(cp, top)` when the flag hits the top or bottom.
8. Top on a neutral CP → captured by the flag team. Bottom on an owned CP → neutralised (team 0).
9. `onlyTakeableByTeam` restricts who can capture. `enemyTicketLossWhenCaptured` deducts tickets instantly.

**Scoring:**

| Event | Points |
|---|---:|
| Capture (first entrant(s) by `enterCpAt`) | 2 |
| Capture assist (the others) | 1 |
| Neutralise | 2 |
| Neutralise assist | 1 |
| Defend (kill an enemy inside your own CP radius) | 1 |

All count as "RPL" (teamwork) sub-score.

**Ticket bleed (`updateTicketLoss`):**

```
A_t = Σ areaValueTeam_t over CPs owned by team t     (areaValue per CP, e.g. 17/20/25/34/50)
for team t with opponent o:
    if A_o >= 100 and A_o > A_t:
        tickets_t -= (ticketLossPerMin_t / 60) * ((A_o - A_t) / 100)    per second
if a team owns 0 CPs and has no living player: that team loses getDefaultTicketLossAtEndPerMin() per *second* (200: effectively instant)
```

Plus −1 ticket per `PlayerDeath` (not on man-down, so a revive saves the ticket). Round end: tickets reach 0 (TicketLimitReached id −1, victory type 3), or the time limit elapses and the team with more tickets wins. Quirks worth preserving or fixing: `totalAreaValue` accumulates incorrectly (unused); team 2's 20% limit uses team 1's tickets.

**Special Forces variant** (`mods/xpack/…/gpm_cq.py`): a `capturingState` CP parameter and `hasGreyCapturingState` (the flag shows grey while contested) replace using `flag` as the state.

### 9.4 Recommendation

**Port the rules to Rust**; they are small and self-contained. Structure the Rust game-mode code around the same seams:

- a `GameRules` trait with event hooks mirroring §9.3;
- a CP component carrying the same parameters, with the engine integrating flag height from `takeOverChangePerSecond`;
- per-team ticket state with `ticketChangePerSecond` and ticket limits.

If original-script compatibility is ever wanted, those seams become a `host` shim. Python 2.3 is the obstacle: use CPython 2.7 via a C FFI, or auto-convert the scripts with 2to3 and embed Python 3 via PyO3. Also note that some behaviour lives in the engine even there: flag integration, trigger volumes, and man-down versus death.

- Both teams get `ai.addSAIStrategy <team> basicAttackEnemy` and `basicGuard`. The vanilla commander is therefore just "attack when enemy or neutral CPs exist, otherwise guard".
- `AIRadioMessages.ai`: `aiComm.addAIRadioMessage "<voice>" <modifier> <maxSendPeriod> <receiveTTL>` (request order, defend, attack position, bail out, get in, medic, need repair, need ammo, …).
- Bot spawn helper `soldier.con`: `game.createAndSpawnAIPlayer`, `ai.addBot <name> <kit> StandardWeights NoEquipment`.

### 10.2 Per-object AI data [verified]

- **`aiTemplate`** (133): `addType IT*` (ITUnit, ITBiological (has a crew), ITGround, ITAir, ITHelicopter, ITNaval, ITMobile, ITHasWreck, ITStructure, ITObstructedView, ITSoldier, ITHasCarHorn), `degeneration`, `allowedTimeDiff`, `basicTemp`, `commonKnowledge`, `secondary`. The knowledge model looks like a "temperature" (salience) that degenerates over time [inferred]. `addPlugIn` references:
  - **Unit** (124): `equipmentTypeName` (maps to a behaviour class), `setStrategicStrength <side> <n>`, `setBattleStrength`, `cullDistance`, `setSelectKey PIPositionSelect2` (the seat key the bot presses), `setHasExposedSoldier`.
  - **ControlInfo** (116): maps the AI's drive/aim/look intentions to input channels (`driveTurnControl PIYaw`, `aimHorizontalControl PIMouseLookX` …) with `*Sensitivity`, `*Scale`, `*LookAhead`, a PD controller (`proportionalConstant -12`, `derivativeConstant -1`, `angleSpeedConstant`), `maxRollAngle`/`maxClimbAngle` (aircraft) and `setCameraRelativeMin/MaxRotationDeg`. **Bots drive vehicles through the same input axes as humans.**
  - **Armament** (77): `setIsAntiAircraft 0/1/2`.
  - **Physical** (57): `setStrType Infantry/LightArmour/HeavyArmour/NavalArmour/Helicopter/AirPlane` (target class).
  - **Mobile** (38): `setPathfindingMap Infantry/Vehicle`, `maxSpeed`, `turnRadius`, `coverSearchRadius`, `setSoundSphereRadius`, `setHearingProbability`, `lodHeight`, `isTurnable`, `vehicleNumber`.
  - **Cover** (17): `coverValue`.
- **`weaponTemplate`** (115): `minRange`/`maxRange` (M16 72 m, M1A2 gun 150, F-18 gun 600), `optimalRangePercentage 35`, `setStrength <class> <n>` (6 target classes), `allowedDeviation` (degrees of aim error tolerated before firing), `indirect`, `setFiringPose Crouching`, `setExplosionRadius`, `setFiresThroughTransparent`, `isThrown`, `weaponActivate`/`weaponFire`.
- **`kitTemplate`** (7): battle and strategic strength per class.

### 10.3 Per-level AI data [verified]

- `ai/AI.ai`: `ai.init 2`, then per-map overrides (Karkand: infantry `maxSlope 43` for steep stairs; `addVehicleForClusterCost`).
- `gamemodes/<mode>/<size>/ai/StrategicAreas.ai`: `aiStrategicArea.create <name> minX/minZ maxX/maxZ <height> <radius?>`, `layer`, then per area: `addNeighbour` (graph), `addObjectTypeFlag ControlPoint`, `setOrderPosition Infantry x/y/z` and `Vehicle x/y/z`, `setSide`, `vehicleSearchRadius`.
  - Karkand cq/32 has 7 areas; **cq/64 is empty** (bots are supported only on the 16-player layer in SP and co-op; the 32-player areas exist for co-op).
- **Navmesh** (per level; absent for Wake Island, Kubra Dam, Blue Pearl, Iron Gator and Leviathan):

The community reports that the BF2 editor exports the level geometry and runs an external navmesh generator built on the open-source **GTS (GNU Triangulated Surface) library** (hence `GTSData`). The editor then builds the quadtree and clusters.

### 10.4 How BF2 bots work: community knowledge plus what the data shows

1. **Strategic layer (SAI, per team, "hive mind"):** evaluates strategy prerequisites (counts of enemy, neutral and owned CPs); picks attack or guard; assigns the requested number of attack and defence "groups" to strategic areas, scored by `setStrategicObjectsModifier` and the area graph; issues orders (radio messages). Tobias Karlsson, BF2's lead AI designer, described the vanilla commander as having essentially two options and the bots as "autonomous drones within a narrow framework".
2. **Squad/group layer:** bots in an order group move to the area's `setOrderPosition` for their movement class, then act locally. Vehicle use is through the `Change` behaviour (`BBChange`), which evaluates nearby vehicles using `Unit` strengths.
3. **Individual layer:** each tick, compute urgency for each behaviour allowed for the current vehicle class (from sensing, the urgency curve and the base priority), multiply by the personality weight set and active inhibitors, and pick the maximum. The behaviour builds a plan of interpreter steps: path to a point via the navmesh (material costs), aim with PD control through the input channels, fire when the aim error is below `allowedDeviation` and the target is in range, choose weapons by `weaponTemplate` strength versus the target `setStrType`. Sensing uses visibility and hearing (`setSoundSphereRadius`, `setHearingProbability`) with knowledge decay (`degeneration`, `allowedTimeDiff`).
4. **Skill:** `setBotSkill 0.0–1.0` (menu, `sv.coopBotDifficulty`) scales reaction and aim error [unknown mapping].

### 10.5 Reimplementation recommendation

- **Navmesh:** generate with **Recast/Detour** at load time or bake time from *our* collision (terrain heightfield + static-object collision meshes + `DestroyableObject` boxes), using BF2's parameters (infantry: radius 0.25, height 1.9, climb 2.5, slope 30–43°; vehicle: radius 3.5, height 3.5, climb 5, slope 20°). Tag areas with nav materials (road, shallows, deep water) and use BF2's per-class costs. This keeps pathing consistent with our physics and works for custom maps. Rust options: `recastnavigation` bindings (`recastnavigation-sys`), or Bevy-native `oxidized_navigation`/`vleue_navigator`. Use `.qti` only as a validation overlay or fallback (it is easy to import now). Use `.ahm` directly for aircraft minimum altitude.
- **Strategic layer:** load `StrategicAreas.ai` as-is: area boxes, neighbour graph, order positions, CP link. Reimplement BF2's two-strategy commander first, then improve with an influence-map or utility scoring over the area graph (frontline = owned areas adjacent to enemy or neutral ones).
- **Squad layer:** explicit squads (leader + 3–5 members) that follow the leader's order position and formation. BF2's own bots are weak here, so this is an easy win.
- **Individual layer:** a **utility AI with the same 13 behaviours**, reusing BF2's weights and urgency curves as initial tuning. Execute actions as a small behaviour tree (sequence, parallel, while, wait), which mirrors BAPST. Drive vehicles through the *same input components as players*, using BF2's ControlInfo PD gains. This gives identical vehicle behaviour and prevents bots from cheating the physics. Target selection: `weaponTemplate.setStrength[targetClass] × range fit`. Aim error: Gaussian with sigma driven by skill, reaction delay and allowedDeviation.
- **Perception:** a per-team knowledge base (spotted objects with salience ("temperature") that decays), line-of-sight raycasts budgeted per tick, and a sound sphere from the `Mobile` plugin.
- Keep bots on the server as ordinary "players" that produce input commands, so netcode, anti-cheat and replays treat them uniformly.

## 11. What cannot be recovered from data, and whether RE is worth it

| Item | Data has | Missing | Impact on feel | Recommended approach |
|---|---|---|---|---|
| **Aircraft lift/drag (Wing)** | coefficients, positions, inputs | force law, stall, units | Very high (jets, helis and parachutes all use Wings) | **RE** the Wing force routine in `bf2_w32ded.exe` (a small function; it must reference `wingLift`/`flapLift` fields); verify by measurement |
| **Engine → force** (Plane, Heli, Tank, NewCar2, Ship) | all parameters | torque/differential/gear/RPM math, NewCar2 tyre curves, track steering, heli angle-of-attack model | Very high | **RE** the per-engine-type update (switch on `c_ET*`); fit remaining constants by measurement |
| Spring / wheel contact, `grip` flags | strengths, damping, flags | units, contact model, flag meanings | High for ground vehicles | RE is small; otherwise tune by feel |
| Rigid-body integration, drag law, inertia from mesh, world gravity | mass, drag, modifiers | integrator, tick, substeps, gravity constant | Medium | Measure (drop tests, coast-down) plus light RE for constants; use Rapier/Avian with a matched fixed step |
| **Soldier movement** (speeds, acceleration, jump, prone and stance speed factors) | vars (`phy-soldier-*`), animation reference speeds, delays | actual m/s, acceleration curve, jump impulse | High | Measure in-game (Python position logging) and tune; RE optional |
| **Deviation accumulation and sampling** | all parameters, community semantics | exact combination, whether stance/zoom scale the accumulators, cone distribution | High (gunplay identity) | RE the SoldierDeviationComp update (small, self-contained); community semantics are a good start |
| Recoil graph | parameters | interpolation formula | Medium | RE or approximate |
| Damage falloff defaults; `minDamage` meaning; explosion falloff curve; default `damageMod` for missing or empty cells | values | the formulas | Medium | RE (small) or empirical tests with the original server (shoot bots at known ranges and read HP via `getDamage()`) |
| Engine defaults for unspecified properties (rpm, magSize, nrOfMags, many others) | – | default constructor values | Medium | RE the template class constructors (often a table of field initialisers) or read the in-game HUD |
| Netcode (ghosting, priorities, prediction, hit registration, lag compensation) | networkable profiles | protocol, rates | None, since we will not interoperate | **Do not RE.** Design modern netcode: server-authoritative, 30–60 Hz snapshots, client prediction for own soldier and vehicle, server-side lag compensation |
| Bot internals (AIDLL.dll): urgency formulas, plan construction, sensing | configuration | code | Medium | Reimplement from the model in §10; do not RE except for curiosity |
| Commander asset timings, squad mechanics, spawn rules (spawn protection, squad spawn), man-down timings beyond `sv.*` | partial | logic | Medium | Reimplement from documented game behaviour |

**Is RE worth it?** Selectively, yes. Vehicle handling and gunplay feel are BF2's signature, and the handful of force and deviation routines are small, isolated and data-driven: they read exactly the fields listed above, which makes them easy to find in Ghidra via the property-name strings. The editor/engine command registration uses string names like `setWingLift`, so cross-references from those strings lead to the setters and hence the struct offsets and consumer functions. Prefer `bf2_w32ded.exe` (no renderer, same simulation) as the target.

Everything else is better served by the **measurement harness**: run the original dedicated server, add a Python module that registers a 30 Hz `bf2.Timer` and logs `getPosition()`/`getRotation()`/`getDamage()` of chosen objects, drive with scripted bot inputs or a human, and fit our models against the curves. The shipped Python API is enough for this. Community reference for this approach: Alon Tavor's ctypes work on the BF2 Python object layout. OpenBattlefield2 is a recent clean-room Refractor 2 reimplementation (MIT) that claims binary-address traceability for its constants. Treat it as a cross-check, not a source to copy, and review its licence and clean-room status first.

## 12. Suggested Rust/Bevy data architecture (driven by the original data)

1. **Asset pipeline:** a `.con` VFS over the user's zips (mount order as in `ServerArchives.con`); a script evaluator (`run`/`include`/`if`/`v_arg`/`var`); a raw `TemplateStore`; typed definitions with defaults and warnings for unknown keys. Keep a "property coverage" report (the per-type census here) to track what is modelled.
2. **Instancing:** a template tree becomes an entity hierarchy. Root PCO = rigid body (compound collider from `collisionmesh` parts; part index → material id via `mapMaterial`). `RotationalBundle` = `Joint1Dof`/`Joint3Dof` components (limits, rate, acceleration, input binding, auto-reset). Force generators = `EngineDef`, `WingDef`, `SpringWheel`, `ForceDef`, `FloatDef` systems that apply forces to the root body in fixed-update order. Seats = nested PCO entities with `Seat {index, camera set, weapons, exit}`. Weapons = `FireArm` entities with component structs mirroring `fire`/`ammo`/`recoil`/`deviation`/`zoom`/`target`.
3. **Input model:** a `PlayerInput` with BF2's channel names (`PIThrottle`, `PIYaw`, `PIPitch`, `PIRoll`, `PIMouseLookX/Y`, `PIFire`, `PIAltFire`, `PIFlareFire`, `PICameraX`, `PIPositionSelect*` …). Joints and engines bind to channels exactly as the data says. Bots write the same component.
4. **Damage:** a `MaterialTable` (143×143 sparse) with `damageMod`, impact FX and penetration; hits resolve (projectile material × hit material); splash uses the victim's `armor.defaultMaterial`; heal/repair/rearm use the same path with materials 73/84/91.
5. **Game modes:** a Rust `GameRules` (conquest, co-op) ported from `gpm_cq.py`; CP, spawner, spawn point and combat area components from `GamePlayObjects.con`; tickets and scoring from `Init.con` and `ScoreManagerSetup.con` plus the Python constants.
6. **AI:** a `StrategicAreaGraph` from `StrategicAreas.ai`; a Recast navmesh; utility behaviours seeded from `AIBehaviours.ai`; per-template `AiProfile` (aiTemplate plugins, weaponTemplate, kitTemplate) loaded straight from the `.ai` files.
7. **Fixed tick:** a 30 Hz authoritative simulation to match BF2's data tuning (deviation decay is per 30 Hz frame; §6.4), with physics substeps as needed and rendering interpolated.
